# 翻译工作台架构设计

> 状态：设计草案，尚未实现。本文把翻译工作台原型映射到 TYN 当前分层规范，供实现前评审；已确认的引擎提取器隔离决策另见 ADR 0003。

开源提取器对比见[翻译文本提取开源参考](翻译文本提取开源参考.md)；翻译任务调度、缓存与工作区参考见[翻译任务开源项目参考](翻译任务开源项目参考.md)；服务目录、API 协议适配和凭据存储参考见[翻译服务接入架构参考](翻译服务接入架构参考.md)。

## 1. 目标与边界

- 妙妙工具中的翻译工作台按游戏管理项目；一个游戏只在首页出现一张项目卡片。
- 提取、翻译、AI 校对是可持久化、可显示进度的后台任务。人工校对是项目内容编辑，不创建后台任务。
- 引擎格式解析彼此隔离；增加或修改一个引擎的提取规则，不改变其他适配器和公共任务流程。
- 翻译服务在应用设置中维护。工作台只选择已配置、已启用且具备当前用途的服务。
- 游戏目录默认只读。项目数据放在 TYN 私有空间，导出由用户在导出动作中选择格式与位置。
- 首期建议覆盖 RPG Maker MV/MZ、CSV 项目导入导出、OpenAI 兼容 API，以及已有运行时支持的 MTool JSON 导出。

本文不是当前功能规格。实现后应把确认的实际行为同步到 `SPEC.md` 与 `ARCHITECTURE.md`。

## 2. 领域概念

- **翻译项目**：以一款游戏为范围的长期工作空间，包含文本条目、译文、术语表、校对结果和导出记录。首页一张卡片对应一个翻译项目。
- **翻译任务**：在项目中执行的一次提取、翻译或 AI 校对操作，有独立进度和终态，可暂停、继续或中止。
- **人工校对**：用户在项目工作区中筛选、编辑和确认文本；不是翻译任务，不显示后台进度条。
- **AI 校对**：可选的翻译任务，为选定条目生成问题提示和建议译文；不会自动覆盖当前译文，之后由用户确认。
- **游戏术语表**：项目内的原文术语与固定译法集合，翻译和 AI 校对可按任务设置使用。
- **运行时译文包**：由工作台项目生成、供游戏运行时查询的只读版本化数据；它与工作台数据库及通用项目导出文件分开。

## 3. 分层与目录

```text
app/src/main/java/com/tyranor/next/
├── core/translation/                  # 新增：工作台业务域，不是游戏运行时
│   ├── project/                       # 项目、条目、术语表的查询与命令
│   ├── extraction/
│   │   ├── TextExtractor.kt           # 引擎提取器契约与规范化结果
│   │   ├── TextExtractorRegistry.kt   # 依 EngineType 选择实现
│   │   ├── shared/                    # SAF 访问、通用文本与占位符规则
│   │   └── engines/
│   │       ├── rpgmaker/mv/
│   │       ├── rpgmaker/mz/
│   │       ├── rpgmaker/rgss/
│   │       ├── tyrano/
│   │       ├── kirikiri/
│   │       └── ...                    # 每个引擎独立注册、独立文件
│   ├── service/                       # 服务目录、协议适配器、模型列表与测试连接
│   ├── task/                          # 持久任务、队列、Worker 与检查点
│   ├── review/                        # 规则检查、AI 建议、人工确认数据
│   └── export/                        # CSV、通用 JSON、运行时译文包等导出器
└── ui/
    ├── tools/translation/             # 妙妙工具入口与工作台 Compose 页面
    └── settings/translation/          # 设置中的机器翻译 / AI 服务列表与配置
```

依赖维持 `ui → core → engine`。工作台提取的是游戏资源文件，不需要启动游戏宿主或依赖 `engine` 的运行时；因此提取器留在 `app/core/translation`。现有 `core/engine/translation` 继续负责运行时译表发现、读取和交付，不与工作台项目或 API 任务混用。

UI 经 ViewModel 发出命令并订阅 `StateFlow`。Core 不导入 Compose 状态或组件；业务失败返回类型化结果/错误码，取消原样传播，由 UI 映射本地化文案。

## 4. 核心数据模型

### 翻译项目

建议以独立 UUID 标识项目，并保存：游戏标题、引擎类型、授权目录 URI（如有）、目录身份指纹、输入类型、语言设置、创建/更新时间和项目修订号。目录路径仅供展示，URI 和当前持有的 SAF 权限才是访问依据。

项目输入来源分为：

1. **游戏目录**：创建待提取项目，选引擎类型。
2. **已提取文本**：导入标准化文本项目，跳过提取进入待翻译状态。
3. **已翻译项目**：导入包含原文和译文的项目，直接进入校对工作区。

同一规范化目录身份原则上只建一个项目。SAF 权限丢失时保留已提取和已翻译内容，标记来源不可访问，并允许重新授权目录。

### 文本条目

每个出现位置保留独立条目，避免相同原文在不同说话人或语境中被强制合并。条目至少保存：稳定 ID、原文、译文、来源定位、出现顺序、翻译状态、规则问题、AI 建议和人工处理状态。

来源定位由引擎适配器生成，供重新提取对账和引擎导出使用；不要求在校对列表显示。说话人或事件信息可作为可选元数据供 AI 请求使用，不占用列表主列，也不要求每种引擎都能提供。

### 翻译任务

每次执行创建独立任务记录，不用一个项目状态字段同时表达阶段、进度和人工校对状态。任务保存：项目 ID、任务类型、状态、开始时的项目修订号、服务配置版本、语言/范围/批次/术语表选项、总数与完成/失败/跳过计数、当前检查点、错误码和时间戳。

项目卡片状态由阶段完成情况与活动任务推导；任务历史记录保留失败、中止和完成结果。删除项目时停止其活动任务，再级联删除项目数据库记录和 TYN 私有项目目录；绝不删除原游戏目录或用户导入的原文件。

## 5. 引擎提取器扩展点

提取器是 TYN 内部的受限 SPI：TYN 通过注册表选择并调用引擎实现，向它提供只读游戏源和条目/进度输出端口；提取器不直接控制任务、Room、UI、网络或项目文件。每种引擎/资源代际有独立包目录和注册项，解析器输出稳定来源 key 与统一文本条目，公共 runner 负责校验、分批保存、进度和取消。

单引擎接入 PR 的目录、接口、注册表约定、边界和评审清单见[翻译提取器接入规范](翻译提取器接入规范.md)。开源提取工具的能力范围见[翻译文本提取开源参考](翻译文本提取开源参考.md)。

重新提取仍按来源定位与旧项目对账：未变化条目保留译文和人工状态，新增/消失/变化条目分别处理，不静默丢弃已有译文。

## 6. 任务管理与状态

### 任务类型与状态

任务类型只有：`EXTRACT`、`TRANSLATE`、`AI_PROOFREAD`。人工校对、筛选、导出不创建后台任务。

```text
QUEUED → RUNNING → COMPLETED
                  ├→ FAILED
                  ├→ PAUSING → PAUSED → QUEUED
                  └→ CANCELLING → CANCELLED
```

UI 可把短暂的 `PAUSING` / `CANCELLING` 合并成即时反馈；数据层保留过渡态，防止用户连续点击造成竞态。失败重试创建新的任务记录或明确的重试代次，成功条目不重做。

### 执行规则

- 单个项目任一时刻最多运行一个会修改项目内容的任务，防止提取、翻译和校对互相覆盖。
- 不同项目的任务进入应用级队列。首期默认全局串行运行一个项目任务；AI API 的“并发请求数”只控制当前任务的请求并发。待真实使用验证后再考虑多个项目并行。
- 任务点击开始后再入队；新建项目只创建“待提取”项目，用户从卡片点击开始。当前 HTML 原型若仍显示“添加并开始提取”，需改为只添加，和此前确定的交互一致。
- WorkManager 负责跨 Activity / 进程重建的执行恢复；Room 是项目、任务和进度的权威状态源，WorkManager 的临时 progress 不作为唯一记录。
- 每一批成功后用单个 Room 事务提交条目结果与检查点。暂停在当前请求结束或取消后生效；中止保留已完成条目；重新开始只处理符合该任务范围的剩余条目。
- 网络任务设置网络约束；长时间后台运行时按 Android Worker 规范提供前台通知。若 SAF 授权失效，任务以明确错误结束，已完成数据保留。

### 进度定义

- 提取：扫描文件数和已发现条目数。扫描未开始时总条目数未知，不显示误导性的 `0/N`。
- 翻译：当前任务范围内“成功 + 失败 + 跳过”的条目数作分母，显示完成、失败计数；已完成结果不因重试消失。
- AI 校对：本次选中范围内已处理条目数作分母，建议数单独统计。完成率不等于问题数或人工已确认数。
- 项目卡片尺寸固定；展示一个阶段条、当前阶段说明和进度条，避免同一百分比在卡片上重复出现。

## 7. 翻译服务与网络

服务配置由单一 `TranslationServiceRepository` 管理，设置页和工作台从同一个 `Flow` 获取服务列表。每个服务声明协议、用途能力、配置/启用状态、端点和模型；AI 服务可具备翻译与 AI 校对能力，传统机器翻译不能出现在 AI 校对选项中。服务保存配置不自动启用。

### 服务适配器

定义统一能力，如连接测试、可选模型列表、批量翻译和批量校对。模型列表是可选能力；服务不支持时保留手动输入模型 ID。机器翻译按 DeepL、Google、Microsoft、百度等固定协议分别实现；AI 服务按 OpenAI 兼容、Anthropic、Gemini 等协议实现。自定义 OpenAI 兼容端点同时覆盖云端和本机其他 APK 暴露的 API，不再把“本地模型”建成 TYN 内置推理后端。

所有实现使用翻译域自己的 OkHttp transport，不把 API 调用散落到 Composable 或任务 UI。初期复用已引入的 OkHttp 依赖，不先重构全 App 网络层。

### 请求与结果

- 一个请求包含稳定条目 ID、原文、源/目标语言、术语表、提示词和可选来源元数据。
- 返回按条目 ID 匹配，不能假设模型会严格按输入顺序或只返回纯 JSON。
- 批次大小同时受服务限制和请求体/上下文长度控制；保护游戏控制码与占位符，校验缺失、重复、额外条目和格式损坏。
- 超时、限流、鉴权错误、服务错误、响应解析错误均转成类型化错误；只对可重试错误做有上限的退避重试。取消必须中断 OkHttp 调用并向上传播。
- 服务、模型、提示词、术语表修订和语言范围共同参与任务快照与缓存键。更改服务配置不应悄悄改变已经启动的任务。
- 默认翻译提示词和校对提示词按服务配置管理；思考强度仅向明确支持该参数的协议发送，关闭时不发送该字段。

API Key 不进入普通 Room 字段、任务快照、导出文件或日志；只保存安全存储引用。现有 `SecureAuthStore` 是登录凭据专用实现，只参考其 Android Keystore AES/GCM 模式，不直接复用其 Hikarinagi 固定字段和别名。

### 任务语言与范围

翻译任务快照包括源语言、目标语言、服务、待翻译范围、每批条数、是否启用游戏术语表和提示词版本。范围至少支持未翻译条目与重新翻译全部条目；重新翻译写入新结果前保留可恢复的当前译文。

## 8. 规则筛选、AI 校对与人工校对

规则检查与 AI 校对是不同来源的问题：规则检查可以在翻译后本地运行；AI 校对由可选 AI 服务产生建议。

- AI 校对范围在开始面板选择：`仅规则命中条目` 或 `全部已翻译条目`。前者节省请求，后者可发现规则未覆盖的语义问题；范围保存在任务快照中。默认项待产品评审确认。
- AI 只读原文、当前译文、所需提示与词表；输出保存为建议和问题标记，不能覆盖当前译文。
- AI 校对任务完成后，项目进入待人工处理状态；卡片提供进入校对的操作。校对方式面板中的 AI 服务区在手动模式下保持可见但不可操作；进入编辑工作区后不显示服务设置，AI 建议区域固定显示“无建议”。
- 列表显示序号、原文、当前译文和状态。手机使用列表页与条目编辑页两级导航；平板使用主从布局。共享同一个筛选和条目状态模型，不复制一套校对业务逻辑。
- 人工可修改译文、采纳建议、忽略问题；“校对完成”在校对详情页操作。完成状态只代表用户结束本轮校对，不代表 AI 或规则检查无问题。

## 9. 持久化、文件和导出

- 新建独立 Room 数据库 `translation_workbench.db`，包括项目、文本条目、任务、问题/建议、术语表与服务元数据；schema 放 `app/schemas/`，以后版本显式 Migration。避免把工作台条目塞进 `game_library.db`。
- 每个项目使用 UUID 私有目录保存临时文件、导入快照和导出暂存；Room 保存可筛选、可编辑的条目。项目删除清理这两处 TYN 数据。
- API Secret 使用 Keystore 加密存储且排除云备份。项目数据库和私有文件属于用户生成内容，实现前需在 `docs/应用持久化数据清单.md` 明确备份/恢复策略；恢复后无 SAF 权限时仍可查看已提取文本。
- 导入使用 `OpenDocument`/`OpenDocumentTree` 并在需要长期访问时持久授权。导出使用系统创建文档流程写到用户选定位置，先写临时文件再提交，不半写目标文件。
- 用户可见的通用导出首期支持 CSV 与标准化项目 JSON；运行时译文包是另一类内部产物，由 TYN 在项目私有目录生成并通过只读 URI 交给运行时模块，不自动写回游戏目录。

### 工作台项目与运行时译文包

工作台数据库是提取、翻译和人工修改后的权威数据。运行时模块不直接读取 Room，也不依赖工作台数据库 schema。启动游戏前，TYN 根据当前项目和目标运行时模块生成不可变的 `RuntimeTranslationArtifact` 快照，并通过运行时桥接接口交付只读 URI；项目后续编辑生成新 revision，不原地改变正在使用的快照。

数据链路固定为：

```text
游戏目录
  → 引擎 TextExtractor
  → 工作台统一条目
  → 翻译服务 / 人工修改
  → RuntimeTranslationExporter
  → 版本化运行时译文包
  → TYN 授权只读 URI
  → 对应运行时模块加载并应用译文
```

运行时包采用显式 `formatId`、`schemaVersion`、`engineId` 和项目 revision。条目包含运行时查找键、原文、译文，以及可选的上下文元数据。运行时查找键必须能由目标模块在显示文本时取得；提取器的 `sourceKey` 只是源文件中的来源定位，不能默认等同于运行时查找键。若引擎只能按原文查找，原文重复且译法冲突时必须报告冲突或采用明确策略，不能静默以最后一条覆盖。

`RuntimeTranslationExporter` 将工作台条目转换成目标模块支持的运行时包。引擎间确实兼容时可复用同一种包格式；键生成或旧格式不同的引擎应在各自的 exporter 目录实现转换。运行时包 schema 版本与通用 CSV/项目 JSON 版本分开管理，不把服务配置、API Key、任务记录或校对内部状态写进包。

### 运行时模块的职责与能力声明

TYN 公共层负责选定活动项目、构建/校验包、保存版本、授予只读访问权限并启动模块。目标运行时模块负责读取自己声明支持的格式、建立查找表，并在引擎文本显示路径中查找和应用译文。模块不得修改原游戏文件。内置模块的实现随 TYN 编译发布；外置 APK 必须自行实现并发布对对应格式版本的支持，TYN 只能依据其能力声明决定是否交付。

模块能力需声明稳定的运行时格式 ID 与支持的 schema 版本范围。当前 `translationRuleId` 用于发现/解析现有译表来源，不能直接复用为工作台运行时包的 schema 版本；能力声明应将“来源译表规则”和“运行时包格式”分开。尚未声明兼容能力的模块不显示工作台项目的运行时加载选项。

TYN 已有 `TranslationMapProvider` 与 engine 侧 `TranslationMapSubscription` 的只读 URI 和更新通知通路，可作为交付机制的实现参考。当前它服务于 MTool JSON 发现与字符串 map 交付，并不等同于完整工作台运行时包协议；新增协议需显式校验 `formatId`/`schemaVersion`，不得把任意项目文件直接交给模块猜测解析。

运行时模块的接入不代替提取器或 exporter：提取器负责从原始游戏资源产生工作台条目，exporter 负责生成运行时可查询的键和目标包，模块负责在运行时消费包并应用译文。只有这三段都实现，且在目标游戏中验收过，才能称该引擎完成端到端翻译接入。对于不能安全插入翻译查找的引擎，应明确标记暂不支持运行时应用，仍可保留提取、翻译和文件导出能力。

## 10. Compose 页面与交互

- 工作台放入妙妙工具，主页面是一款游戏一张项目卡片；筛选统计从项目阶段与活动任务派生。
- 卡片根据阶段显示“开始提取 / 开始翻译 / 开始校对 / 导出 / 删除”等可用操作。导出在卡片操作中选格式与目标位置，不放进提取或校对详情页。
- 新项目选择提取、翻译或校对来源。提取只要求游戏目录与引擎类型；已提取/已翻译项目经文件选择器导入。
- 翻译启动面板选择语言、已启用服务、范围、批次大小和术语表；确认后立即创建翻译任务并回到项目列表看进度。
- 校对启动面板选择 AI 或手动。手动立即进入编辑，不要求 AI 服务；AI 校对选 AI 服务和校对范围，启动后回到项目列表显示进度。
- 手机校对采用列表到详情的单页切换；平板在同页并排显示列表和编辑器。表格滚动区、固定表头、筛选面板与触控尺寸按已有 UI 规范实现。
- 二级页面使用 `AppSecondaryTopBar` / `AppScreenScaffold`；设置页使用当前设置页宿主与 Miuix 规范。服务选择器、筛选面板和弹窗复用公共组件及动效入口。

## 11. 错误与恢复场景

Core 返回错误码而不组装中文文案，至少区分目录不可读、SAF 授权失效、格式不支持、资源损坏、无可提取文本、服务未启用、鉴权失败、限流、超时、响应无效、可重试网络失败和存储失败。

以下行为作为实现验收约束：

- 翻译请求成功但进程在写库前退出：该批保持未完成，重启后可重发；已提交批次不重翻。
- API 返回部分结果：有效条目提交，缺失/无效 ID 的条目单独失败并可重试。
- 用户中止时：保留已完成条目和错误原因，不清空整个项目。
- 任务运行时删除项目：先撤销任务并等待 Worker 不再提交，然后删除项目数据；迟到回调不能重建已删除项目。
- 重新提取游戏更新内容：按来源定位匹配，保留未变条目的译文；变更条目需明确标出。
- 服务配置在任务运行中被编辑/停用：任务继续使用启动时的非秘密配置快照，密钥引用失效时转成可见错误，不静默切换到另一个服务。

## 12. 分阶段实现

1. **项目与 MV/MZ 提取**：Room、项目卡片、SAF 目录读取、MV/MZ 独立适配器、CSV/JSON 导出；以真实游戏核对可见文本覆盖和来源定位。
2. **翻译闭环**：服务配置持久化、OpenAI 兼容服务、模型获取/手输、Key 加密、批量翻译、断点续跑和术语表；译文保存在工作台项目中。
3. **校对闭环**：规则检查、可选 AI 校对任务、AI 建议和人工编辑/完成状态。
4. **MV/MZ 运行时闭环**：由工作台项目生成兼容的 MTool JSON 运行时包，经现有只读 map 通路交付，并在真实游戏里验收译文查找与显示。
5. **扩展引擎与传统 API**：按 ADR 为各引擎分别添加提取器、必要的运行时 exporter 和模块加载/应用能力；按服务协议新增固定机器翻译适配器。只有完成并验收这些环节的引擎才标记为端到端支持。

每个新引擎需有针对其格式的解析夹具与至少一个合法样本；提取成功本身不能替代导出后在真实游戏中的显示验收。项目和服务的 UI 文案同步三种语言，Room schema、持久化清单、`SPEC.md`、`ARCHITECTURE.md` 和 `README.md` 在对应功能落地时更新。

## 13. 待产品确认

1. AI 校对默认处理全部已翻译条目，还是只处理规则命中条目。原型需给用户明确选项；目前不把默认值写死。
2. 首期是否只支持 MV/MZ 的原始游戏目录，还是同时接收外部提取器生成的标准 CSV/JSON 项目。
3. 用户切到后台后任务是否继续。若继续，需要 WorkManager 前台通知；若只在工作台前台跑，进程被回收后仍保留检查点并允许手动继续。
4. 翻译服务首期启用哪些固定机器翻译模板与 AI 协议；自定义 AI 的非标准 HTTP JSON 应晚于协议适配器稳定后再决定。
