# 翻译文本提取开源参考

> 范围：整理公开项目的文本提取/回填能力，供 TYN 翻译工作台设计参考。项目 README 的支持表表示格式覆盖声明，不代表每款游戏的全部可见文本都能自动提取，也不代表可以直接在 Android 中运行。

## 1. TYN 当前引擎范围

`EngineType` 共定义 29 个值。去掉 PC、Android 应用、PSP、Nintendo Switch、Unknown，以及代表动态第三方运行时模块的通用类型后，有 23 个固定引擎类型；其中 `VN` 和 `WebOther` 是宽泛分类，不等于两个具体的资源解析器。

RPG Maker 在 TYN 中分为 `RPG Maker RGSS`、`RPG Maker MV`、`RPG Maker MZ` 三个类型；RGSS 覆盖 XP、VX、VX Ace 代际。第三方运行时模块可由任意 APK 承接，数量不是固定值。

当前 `core/engine/translation/TranslationCatalog` 处理的是**已有译表的发现和运行时交付**：内置固定规则覆盖 MV/MZ 的 MTool JSON；外部运行时须声明已注册的翻译规则。这不等于工作台已实现游戏文本提取。

代码来源：[EngineType.kt](../app/src/main/java/com/tyranor/next/core/engine/EngineType.kt)、[TranslationCatalog.kt](../app/src/main/java/com/tyranor/next/core/engine/translation/TranslationCatalog.kt)、[当前翻译架构说明](../ARCHITECTURE.md#翻译功能)。

## 2. RPG Maker 专用项目

### rvpacker-txt-rs

[RPG-Maker-Translation-Tools/rvpacker-txt-rs](https://github.com/RPG-Maker-Translation-Tools/rvpacker-txt-rs) 声明支持 RPG Maker **7 个代际**：2000、2003、XP、VX、VX Ace、MV、MZ。`read` 可提取可翻译文本到纯文本条目，`write` 可把译文写回原始格式；旧版资源归档可在读取流程中解包。它基于 `rvpacker-txt-rs-lib`，适合进一步研究解析库与 CLI 的职责边界。

需要重点借鉴的工程问题：

- 旧代际 LCF、Ruby Marshal、RGSS 归档与 MV/MZ JSON 是不同格式，不能只凭“RPG Maker”做一个解析分支。
- 各代际的文本编码不同；读入编码和写回编码需要分别处理。
- 输出条目带有来源结构标记，才能正确把文本回填到对应游戏数据。
- 项目支持读取与回填，但其 README 不宣称任意插件或脚本内字符串都会被找到。

当前发布页提供 Windows/Linux 构建，没有 Android 成品；源码/库可以作为解析参考或后续构建评估对象，不能直接把桌面程序当作 TYN 的 Android 组件。[README](https://github.com/RPG-Maker-Translation-Tools/rvpacker-txt-rs/blob/main/README.md) · [发布说明](https://github.com/RPG-Maker-Translation-Tools/rvpacker-txt-rs/releases)

### rpgmtranslate-qt

[RPG-Maker-Translation-Tools/rpgmtranslate-qt](https://github.com/RPG-Maker-Translation-Tools/rpgmtranslate-qt) 是桌面 CAT 编辑器，支持同样的 7 个 RPG Maker 代际，并把格式解析/回填交给独立库。它适合研究项目目录、逐文件条目、纯文本译文、增量重读和回填前备份等工作流。其 README 标注 WTFPL；引入代码或依赖前仍须逐项检查第三方库许可证与 TYN 的打包要求。[README 与许可证说明](https://github.com/RPG-Maker-Translation-Tools/rpgmtranslate-qt/blob/main/README.md)

## 3. 视觉小说多引擎提取项目

### VNTextPatch

[arcusmaximus/VNTranslationTools](https://github.com/arcusmaximus/VNTranslationTools) 中的 VNTextPatch 当前支持表列出 **22 种引擎/脚本格式**：AdvHD、ArcGameEngine、Artemis、Buriko/Ethornell、CatSystem2、Cyberworks C,system、KaGuYa、Kirikiri、Majiro、Musica、Mware、Propeller/Stuff Script、RealLive、Ren'Py、ShSystem、Silky's/AI6WIN、Qlie、Softpal、SystemNNN、TmrHiroAdvSystem、Whale、YU-RIS。工具目标是从原脚本提取文本并把译文打回相应格式。

它与 TYN 固定引擎类型有明确重叠，包括 Artemis、Ethornell/BGI、CatSystem2、Kirikiri、RealLive、Ren'Py、SystemNNN、YU-RIS。不同格式有各自的扩展名、命令行模式和编码要求；例如部分格式没有可自动识别的扩展名，需要显式指定格式。支持表不是“一个通用解析器覆盖所有脚本”。该仓库已于 2023 年归档，许可证为 MIT；其代码以 C# 桌面工具为主，可供解析规则参考，不能直接视为 Android 可集成组件。[VNTextPatch 支持表与说明](https://github.com/arcusmaximus/VNTranslationTools/blob/main/README.md) · [仓库状态与许可证](https://github.com/arcusmaximus/VNTranslationTools)

### RPGMTL

[MizaGBF/RPGMTL](https://github.com/MizaGBF/RPGMTL) 采用文件格式插件处理 RPG Maker、Ren'Py、YU-RIS、Kirikiri/KAG、NScripter、Triangle/Lusterise 等资源，并同时接受 JSON、JavaScript、CSV、INI、TXT 与字幕等通用格式。它是多引擎工具，不宜用单一“支持 N 个引擎”的数字概括：通用文本格式、脚本插件和完整引擎解析不是同一覆盖级别。

它的前置步骤说明了“能解析脚本”与“能直接从游戏目录提取”的区别：Kirikiri 需要先从 XP3 解出脚本；NScripter 流程需要外部反编译，再把译文重新编译。RPGMTL 还允许用户自定义 Patch/Fix 代码，文档明确提醒导入外部项目时检查代码；TYN 不应执行游戏目录或导入项目提供的任意脚本。[支持格式与安全说明](https://github.com/MizaGBF/RPGMTL/blob/main/readme.md) · [Kirikiri 前置步骤](https://github.com/MizaGBF/RPGMTL/blob/main/readme/plugins/kirikiri.md) · [NScripter 前置步骤](https://github.com/MizaGBF/RPGMTL/blob/main/readme/plugins/nscripter.md)

### GalTransl 的边界参考

[GalTransl](https://github.com/GalTransl/GalTransl) 的提取流程组合 VNTextPatch、SExtractor 等专用工具，把结果整理为统一的 JSON 对话条目，再交给翻译与校对流程。它适合参考“引擎专用提取器 → 稳定中间格式 → 通用翻译任务”的边界。项目文档也指出，同一引擎下并非每款游戏都能成功提取，因此 TYN 应记录格式/样本验证结果，不能只显示一个引擎名称就宣称全面支持。[GalTransl 提取与工作流说明](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md)

## 4. 覆盖范围比较

| 参考项目 | 明确支持数量 | 主要覆盖 | 提取之外的前置条件/边界 |
|---|---:|---|---|
| rvpacker-txt-rs | 7 个 RPG Maker 代际 | RM2K/2003、XP/VX/VX Ace、MV/MZ | 编码、归档和写回都按代际处理；桌面发布物不是 Android 组件 |
| VNTextPatch | 22 个引擎/脚本格式条目 | 多种视觉小说脚本 | 有些需显式格式标识；某些脚本/游戏还需先解包；仓库已归档 |
| RPGMTL | 不适合压成一个引擎数 | 引擎插件 + JSON/JS/CSV/TXT 等通用文件格式 | 不同插件的提取、解包和回填能力不同；部分流程调用外部工具 |
| GalTransl | README 未以统一数字统计 | 通过外部提取器导入统一 JSON | 更适合作为通用翻译流水线参考，不是单体万能提取器 |

这些数字不能相加。VNTextPatch、RPGMTL 与 RPG Maker 工具之间有重叠，且每个工具对插件命令、加密归档、图片文字和动态脚本的覆盖不同。GalTransl 的说明也明确提醒，某引擎有工具支持不保证该引擎的每个游戏都能提取。[GalTransl 支持边界说明](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md)

## 5. 对 TYN 提取器设计的建议

### 适配器边界

- 每个引擎/代际独立实现提取器，由 `TextExtractorRegistry` 按 `EngineType` 选择。MV/MZ 可共享 JSON 工具函数，但各自维护提取规则；RGSS 不并入 JavaScript/JSON 解析器。
- Core 提供通用 SAF 文档读取、任务进度、取消、项目保存和错误协议。引擎提取器只负责识别自己的文件结构并产出条目，不访问 UI、Room、网络服务或任意游戏脚本运行环境。
- 统一条目保存稳定 ID、原文、来源定位、文本类型和必要的可选元数据。来源定位用于重复提取对账及后续 exporter；不必显示在校对列表中。
- exporter 独立于 extractor。解析器可以先支持提取和 CSV 导出，后续再增加可回填到某引擎的 exporter。

### SAF 与文件安全

- `ScanGame.uri` 可能是 `content://`，不得把它直接交给 `File(uri)`。通过 `ContentResolver`/文档 URI 流式读取；一个项目目录的读取权限失效时以类型化错误结束任务，保留已提取数据。
- 不在游戏原目录写入、不执行游戏脚本、不自动调用外部可执行文件。解包与格式支持显式记录前置条件，避免误报“自动提取全部文本”。
- 重新提取生成新快照；稳定来源定位且原文未变的条目保留译文，新增/删除/变化条目分别标识，不静默覆盖人工结果。

### 首期顺序

1. RPG Maker MV/MZ：JSON 结构相对明确，且 TYN 现有运行时已经能加载 MTool JSON 字符串映射，可验证“提取 → 翻译 → 导出 → 运行时使用”的闭环。
2. RPG Maker RGSS：按 XP/VX/VX Ace 的 Ruby Marshal、RGSS 归档和文本编码拆分代际实现。
3. 依据真实游戏需求选择 VNTextPatch 重叠较高的引擎逐个接入；每个适配器独立记录文件覆盖、插件限制、样本和回填验收状态。

每种格式的验收至少分成“能解析样本”“可见文本覆盖已人工检查”“导出后目标引擎实际显示”三项。只完成第一项时，不应把该引擎标成完整支持。

## 6. 与 TYN 架构草案的关系

本参考文档补充[翻译工作台架构设计](翻译工作台架构设计.md)中的引擎适配器选择。逐个引擎接入 TYN 的接口、注册与 PR 规范见[翻译提取器接入规范](翻译提取器接入规范.md)；按引擎隔离提取器的架构决策见 [ADR 0003](adr/0003-translation-extractors-per-engine.md)。本文只列公开项目的能力和设计参考；代码复用前须单独核对许可证、第三方依赖、Android 构建可行性及 SAF 接入方式。
