# 翻译提取器接入规范

> 状态：工作台实现前的接入规范草案。适用于妙妙工具中的游戏文本提取；不适用于运行时译表加载，也不意味着当前版本已经实现该能力。

本文把“每个引擎独立提取”落成可执行的目录、接口、注册和 PR 约定。整体模块位置见[翻译工作台架构设计](翻译工作台架构设计.md)，开源工具覆盖比较见[翻译文本提取开源参考](翻译文本提取开源参考.md)。

## 1. 核心约定

提取器采用 TYN 内部的静态扩展点：TYN 定义契约并调用提取器，提取器只实现自己的资源解析规则。它不是可执行插件，也不是让引擎代码任意指挥 App 的通用接口。

- TYN 公共层负责目录授权、只读文件访问、任务排队和状态、进度持久化、取消、条目写库、错误映射与重新提取对账。
- 单个提取器只负责判断自己的资源是否满足前置条件、解析自己支持的文件，并输出统一文本条目和来源定位。
- 提取器不能直接访问 Room、任务表、设置、UI、网络/API、其他引擎实现或任意文件系统路径；不能写入游戏目录、执行游戏脚本或启动外部程序。
- 每种引擎/资源代际有独立实现与测试。添加一种格式不要求修改其他提取器或公共任务流程。

因此，“暴露接口”的方向是 **TYN 把受限能力交给提取器使用**：提取器通过只读源接口读取文件，通过输出端口交回条目、进度和诊断。任务和数据仍由 TYN 掌控。

## 2. 代码目录与隔离粒度

建议结构：

```text
app/src/main/java/com/tyranor/next/core/translation/extraction/
├── api/                              # 稳定契约与标准化输出
│   ├── TextExtractor.kt
│   ├── TextExtractorDescriptor.kt
│   ├── ReadOnlyGameSource.kt
│   └── ExtractionOutput.kt
├── TextExtractorRegistry.kt          # 唯一的静态注册名单
├── runner/                           # TYN 公共任务编排，不放引擎解析规则
├── shared/                           # SAF、流读取等真正通用的工具
└── engines/
    ├── rpgmaker/mv/RpgMakerMvTextExtractor.kt
    ├── rpgmaker/mz/RpgMakerMzTextExtractor.kt
    ├── rpgmaker/rgss/RgssTextExtractor.kt
    ├── tyrano/TyranoTextExtractor.kt
    └── ...
```

隔离单位是**独立包目录和注册项**，不是每个引擎一个 Gradle module。简单实现可只有一个 `*TextExtractor.kt`；解析器复杂时可在自己的目录增加私有 reader、decoder 和格式模型文件，不应为了“一个引擎一个文件”把逻辑挤成巨型类。多个世代的资源结构不同（例如 RPG Maker MV/MZ 与 RGSS）时，分别维护提取器；只共享与引擎无关的文件流、路径检查等工具。

工作台解析器位于 `app/core/translation`，不放 `engine/`。它读取游戏资源但不启动游戏宿主、不依赖引擎运行时，也不让底层引擎模块依赖 App UI。

## 3. 提取器契约

实现时的接口可以按项目 Kotlin 风格细化，职责至少应等价于：

```kotlin
interface TextExtractor {
    val descriptor: TextExtractorDescriptor

    suspend fun preflight(source: ReadOnlyGameSource): ExtractorPreflight

    suspend fun extract(
        source: ReadOnlyGameSource,
        output: ExtractionOutput,
    ): ExtractionSummary
}

interface ReadOnlyGameSource {
    suspend fun list(relativePath: String): List<GameDocumentInfo>
    suspend fun open(relativePath: String): InputStream?
}

interface ExtractionOutput {
    suspend fun emit(entry: ExtractedTextEntry)
    suspend fun report(progress: ExtractionProgress)
    suspend fun report(diagnostic: ExtractionDiagnostic)
}
```

这是职责示意，不要求照抄类型名。实现时应避免把 `Context`、Room DAO、`File` 根路径或 Compose 状态交给引擎解析器。`ReadOnlyGameSource` 只接受相对路径并将访问限制在用户授权的项目目录内；读文件以流为主，避免把大型资源一次性读入内存。缺少、不可读或格式不支持通过类型化结果/错误码报告，文案由 UI 映射。

### Descriptor

每个适配器注册稳定的 `extractorId`，并声明：

- 对应的 TYN `EngineType` 或受支持的资源代际；
- 支持的文件/格式版本和必要前置条件；
- 输出条目 schema 版本；
- 可用于任务日志的稳定能力标识，不在 Core 返回本地化 UI 文案。

注册项必须唯一。ID 一旦进入项目/任务记录就不应因重命名而随意改变；确需迁移时提供显式兼容映射。

### 输出条目

提取器输出统一 `ExtractedTextEntry`，至少包含：

- 稳定的 `sourceKey`：来自相对文件路径与格式内结构位置，用于重新提取时匹配同一出现位置；
- `sourceText`：原文；
- 可选的文本类型、说话人/上下文和安全的来源元数据；
- 必要时的控制码/占位符信息。

相同原文在不同位置仍输出为不同条目，不在提取器里按文本去重。条目 ID、项目 ID、译文状态和任务状态由公共层创建/维护。来源位置应可序列化且不含设备绝对路径、SAF 临时 URI 或不可移植的文件句柄。

## 4. 调用流程与责任边界

```text
用户选择游戏目录与类型
        ↓
TranslationTaskRunner 创建/恢复任务
        ↓
TextExtractorRegistry 按 EngineType 取唯一实现
        ↓
preflight（检查可读性、格式与前置条件）
        ↓
extract（只读源文件 → 输出标准条目/进度/诊断）
        ↓
Runner 分批校验并写入 TYN 项目数据库
        ↓
任务状态与进度由 TYN 更新，导出器另行消费标准条目
```

提取器不得自行创建 WorkManager、改任务状态、决定重试、直接写入 Room 或导出文件。`ExtractionOutput.emit` 是交回条目的窄接口；实际校验、事务、检查点和写库仍由 TYN runner 实现。每个输出批次成功提交后才能推进持久进度。协程取消必须原样传播，公共层负责结束当前任务；提取器不能吞掉取消后继续读文件。

`preflight` 应快速检查必要目录/文件、格式代际或解包前置条件，不扫描全盘。若格式需要用户先解包或当前版本不支持，应以结构化诊断明确说明，不要伪报“提取完成、0 条”。

## 5. 注册与“启用”

`TextExtractorRegistry` 是 TYN 内的唯一静态 allowlist：

```kotlin
private val extractors = listOf(
    RpgMakerMvTextExtractor,
    RpgMakerMzTextExtractor,
    RgssTextExtractor,
).associateBy { it.descriptor.engineType }
```

新实现只有进入注册表后才会被工作台发现和调用。这里的“启用”指 App 代码中注册此实现、随 TYN 版本发布；它不是服务列表里的运行时开关，也不是用户安装任意脚本即可扩展。注册表应在初始化时检查重复 `EngineType`/重复 ID，并让未注册类型返回“当前不支持提取”的类型化结果。

当前已有的 `EngineType` 可直接增加注册项。若新增引擎类型本身，还需要另行修改 `EngineType`、引擎显示资源和相关识别/导入入口；这不是仅添加提取器就能完成的功能，也不能借提取 PR 宣称该引擎已可启动游戏。

## 6. 共享代码与变更影响

新引擎优先在自己的目录实现解析，不为一次接入修改其他引擎文件。只有多个适配器确实使用相同、无引擎语义的操作时，才将其提取到 `shared/`，例如受限流读取、路径规范化或通用占位符扫描。引擎特有的编码猜测、脚本语法、资源命名规则和容错策略不能放进 shared。

公共契约需要演进时，应先证明多个引擎都需要该能力，并保证旧适配器有明确迁移路径。新增可选字段应有默认值；禁止为了一个解析器将另一个适配器的行为改成分支开关。Registry 只做注册和路由，不包含解析细节。

任务 runner 以提取器 ID 选择一个实现，失败被限定为当前项目任务；适配器不得持有跨任务的可变游标、文件缓存或项目状态。共享 reader 应无状态，或将状态明确限制在单次提取会话中。这样可避免一个引擎的运行状态污染另一个引擎。

## 7. 单引擎 PR 的最小范围

对一个 TYN 已认识的引擎类型，正常新增提取支持的 PR 应包含：

1. 该引擎隔离目录中的提取器实现，以及只服务该实现的解析辅助文件；
2. `TextExtractorRegistry` 中的一条注册项；
3. 该引擎自己的最小合法/异常样本与解析回归测试，验证条目、来源 key、排序、错误与取消边界；
4. 更新提取覆盖说明：格式版本、可提取文件范围、已知插件/归档限制、样本验证情况。

通常不需要修改其他引擎的提取器、通用任务状态机、服务/API 层、UI 页面或导出器。若确需公共契约或 shared 工具变化，PR 需说明至少两个使用场景、兼容影响和回归覆盖；若引擎类型尚不存在，则补齐类型和用户可见名称资源，并明确游戏启动支持仍需独立实现与验收。

测试与 fixture 必须属于对应引擎目录/包，不能把某个引擎的真实格式夹具塞进通用提取器测试后再用引擎条件判断。样本应可合法分发且去除个人游戏内容；不能提交未经许可的完整商业游戏资源。

## 8. PR 评审清单

- [ ] 只有注册表将选定 `EngineType` 路由到该实现；未知类型不会回退到猜测性解析器。
- [ ] 解析器只通过授权只读源访问相对路径，不访问任意绝对路径、不写游戏目录、不执行脚本。
- [ ] 同一原文的不同来源位置不会错误合并，`sourceKey` 在重复运行中稳定。
- [ ] 输出能被公共层校验并流式/分批持久化；失败或取消保留已提交结果。
- [ ] 解析规则、编码、前置条件、已知覆盖边界写进该引擎的说明与样本测试。
- [ ] 没有把引擎特有逻辑塞入 shared、runner、其他引擎或 `engine/` 运行时模块。
- [ ] 真实游戏的覆盖与导出/运行验收状态如实记录；通过解析夹具不能宣称全面兼容。

## 9. 一句话回答

是的，目标就是“每个引擎独立实现，按 TYN 约定接入注册表，公共流程统一调度”。对已有引擎类型，PR 的核心是**引擎自己的提取代码 + TYN 注册名单 + 自己的夹具/回归测试与支持说明**；注册项负责让 TYN 启用它。接口限制提取器只能读取输入并产出标准条目，因此每个引擎不会直接操纵 TYN 的任务和数据库，也不需要修改别的引擎逻辑。
