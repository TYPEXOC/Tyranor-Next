# 翻译任务开源项目参考

> 状态：调查参考，尚非实现规格。核查日期：2026-11-16。本文参考项目公开的 README、使用说明和版本记录；功能描述以各项目自己的声明为准，不代表我们对所有游戏或 API 组合做过兼容验证。

本文聚焦翻译工作台中的**批量翻译任务**：如何拆批请求、保存部分结果、失败后续跑、管理词条状态，以及如何从自动翻译过渡到人工确认。文本提取器的项目对比见[翻译文本提取开源参考](翻译文本提取开源参考.md)；TYN 的目标结构见[翻译工作台架构设计](翻译工作台架构设计.md)。

## 1. 结论

- **任务调度、缓存与失败恢复：优先研究 GalTransl。** 它直接面向视觉小说长文本翻译，公开说明了断点续跑、译文缓存、批次上下文、词典和失败拆分重试。
- **逐条翻译与人工编辑：研究 Translator++、RPGMTranslate。** 它们强调翻译表格、保留控制码、按上下文区分同文、搜索和人工改译。
- **RPG Maker 项目状态与保存：研究 RPGMTL。** 它展示了单游戏项目、项目级配置、条目忽略/去重处理、备份与发布目录的基本操作。
- 这些是桌面或本地服务项目，不能作为 TYN Android 的现成任务引擎。TYN 应借鉴数据边界和操作语义，按自己的 Room、WorkManager、SAF 与网络层规范实现。

## 3. 值得细看：GalTransl

### 3.1 翻译结果先落缓存，再生成结果文件

GalTransl 把每个输入脚本对应的翻译缓存作为可续跑状态：翻译先写缓存，脚本完全处理后才生成最终译文文件。缓存条目还保留处理前后原文、初译、校对译文、翻译者/模型、问题标记等数据。加入词典后，只有相关缓存失效或需要更新的条目才会再次请求。[缓存字段、生成流程与错误分析说明](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md)

对 TYN 的启发：**每条翻译结果应可独立落库，任务进度不能只靠一次 API 请求的内存状态。** TYN 用 Room 保存条目状态和任务检查点；按批请求时，先校验响应，再用一个数据库事务提交该批可用结果与计数。不要把项目里的某个临时 JSON 文件作为唯一权威状态。

### 3.2 批次要受上下文预算控制

GalTransl 支持连续批次共享对话上下文，并按轮数、字符预算重开会话；重开时可带上最近若干条译文作为上下文种子。新版本也加入了试译、停止任务、失败时缩小批次并减少上下文后重试等处理。[上下文与批次配置](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md) · [近期发布记录](https://github.com/GalTransl/GalTransl/releases)

对 TYN 的启发：单批条数只是设置上限，实际请求还要受服务 token/context 限制。AI 批次可以附带角色、邻近对话和术语，但这些是发给模型的上下文，不必塞进校对表格列里。超过长度或响应格式不合法时，优先拆小重试；不能将整批都记为失败而丢弃已经解析出的有效条目。

### 3.3 失败、恢复和可见进度

公开版本记录提到过自动续跑、失败批次拆分重试、并发分片调度，以及调整分割参数后继续复用缓存；也修正过进度提前到 100%、失败条数不准等问题。桌面端任务卡提供停止操作和运行状态标识。[GalTransl 功能说明](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md) · [发布记录](https://github.com/GalTransl/GalTransl/releases)

对 TYN 的启发：进度、失败数和剩余数应由持久化的条目结果推导；失败条目要可筛选、可单独重试；取消任务保留已完成结果。切换任务配置或批次大小后，只有明确匹配的旧结果才能复用，不能只按“第几批”复用缓存。

### 3.4 词典分层和问题筛选

GalTransl 同时使用项目角色/设定字典、通用 GPT 字典、译前字典、译后字典和条件替换，并把标点、日文残留、换行差异、疑似不通顺等问题记录到翻译缓存中。[字典与问题检查](https://github.com/GalTransl/GalTransl/blob/main/README_EN.md)

对 TYN 的启发：游戏术语表应是项目资产；任务开始时记录所用的术语表版本。规则扫描产生的问题和 AI 校对建议应保留来源类型，筛选 UI 可以合并展示，但不能混为一种“AI 判定”。固定译法需要避免无上下文的全局机械替换。

## 4. 其他项目的补充经验

### Translator++：同一句不保证同一译文

Translator++ 将翻译服务与表格编辑器分开，支持控制码保护、翻译记忆、上下文信息、多个 AI 候选及人工审校。它也明确允许同一原文在不同游戏位置保留不同译文。[项目流程与特性](https://github.com/TranslatorPlusPlus/TranslatorPlusPlus/blob/main/README.md)

这与 TYN 当前“每个出现位置是独立条目”的设计一致。可选的复用机制应基于明确的翻译记忆匹配，并允许用户改写单条结果；不应默认把所有相同原文绑定到同一个译文。仓库标注 GPL-3.0，参考设计不等于允许复制代码。

### AiNiee：将“翻译服务”和“游戏提取”分开

AiNiee 的游戏流程说明先配置 AI 接口，再导入原文文件夹开始翻译；游戏文本通常需要 MTool、Translator++、Ren'Py SDK 等外部工具准备。提示词可包含术语、角色、背景与翻译风格。[AiNiee README](https://github.com/NEKOparapa/AiNiee)

这支持了 TYN 已确定的分层：提取负责产出统一条目，翻译任务消费条目； API 服务配置由设置页维护，任务启动时选择使用的已启用服务。AiNiee 标注 AGPL-3.0，应视为流程参考，代码复用需另行评估许可证。

### RPGMTL 与 RPGMTranslate：工作区编辑应保留粒度

RPGMTL 将工程、文件和文本条目组织成层级，允许忽略文件/词条，并允许重复文本默认联动、对语境不同的特例解除联动；它还记录上次提取产生的变化并创建备份。[RPGMTL 项目与编辑说明](https://github.com/MizaGBF/RPGMTL/blob/main/readme.md)

RPGMTranslate 提供书签、搜索、批处理、术语和控制码检查等编辑能力。[rpgmtranslate-qt README](https://github.com/RPG-Maker-Translation-Tools/rpgmtranslate-qt/blob/main/README.md) 这些能力适合后续扩展工作台校对页；首期的自动翻译任务不需要把桌面 CAT 的所有功能都塞进任务卡片。

## 5. 建议落到 TYN 的翻译任务模型

### 5.1 三种状态分开存

不要用一个百分比或一个状态同时代表项目阶段、当前任务执行和每条文本译文状态：

| 对象 | 保存内容 | 例子 |
|---|---|---|
| 翻译项目 | 这款游戏的长期资料、条目、语言和术语表 | 已提取、待翻译、翻译完成、待校对 |
| 翻译任务 | 一次翻译运行的状态、配置快照、计数、检查点、错误 | 排队、运行中、暂停、已取消、失败、完成 |
| 文本条目 | 单条原文/译文以及可重试状态 | 待翻译、已翻译、失败、跳过、人工修改 |

用户从项目卡片开始翻译后创建一条任务。任务完成不意味着人工校对完成；项目卡片的阶段标签由条目结果和活动任务状态推导。人工编辑直接修改项目条目，不另建后台任务。

### 5.2 每个任务冻结运行配置

开始任务时记录服务 ID、服务配置版本、模型 ID、源/目标语言、任务范围、批量上限、并发数、提示词版本和术语表版本。Key 仍放安全存储，只在任务里留安全引用。之后编辑服务设置不应悄悄改变正在运行的任务。

如任务使用“仅未翻译文本”，启动时应确定本次条目集合或可复现的范围快照。用户选择“重译”时，新结果先作为新版本或可撤销变更保存，不能覆盖后不可恢复。

### 5.3 请求批次与结果提交

1. 从任务范围选出待处理条目，按服务限制和上下文预算切批。
2. 给每条请求附稳定条目 ID；需要时附最少的说话人/邻近文本、提示词与术语表命中项。
3. API 响应按 ID 对应，不依赖数组顺序。校验缺少、重复、额外 ID、空译文、控制码/占位符损坏。
4. 对通过验证的条目独立保存；部分响应只让无效条目失败，不回滚有效结果。
5. 记录检查点与汇总进度后调度下一批。每批结束和应用恢复时都能重建准确状态。

网络超时、连接失败、限流和部分服务错误可按上限退避重试；鉴权失败、模型不可用和输入不受支持等错误应提示用户修配置，而不是无限重试。暂停停止派发新批次并让正在运行的请求安全收尾；中止停止后续工作且保留已经提交的译文。恢复只继续待处理/可重试条目。

### 5.4 进度的口径

- 提取未完成前条目总数未知，不显示 `0/N`。
- 翻译进度按本次范围内已成功、失败或跳过的条目数计算；错误数单独显示。
- 进度和任务状态从持久化记录计算，不能只读某个 Worker 的瞬时进度。
- 试译是正式翻译前的短任务/预览，用来确认文风和配置；确认后再开始全量任务。
- 任务卡只显示这次在做什么、计数/进度和必要的暂停/中止操作；配置留在任务开始面板，任务启动后不再允许改参数。

## 6. 首期范围建议

结合现有架构草案，首期可收敛为：

1. 翻译任务从项目中选取“未翻译条目”；另外提供显式的重译入口。
2. 任务启动时选择源/目标语言、已启用的机器翻译或 AI 服务、AI 批次数/并发、项目术语表开关。
3. 以服务适配器统一请求结果，以 Room 记录条目状态、运行快照和已提交结果；后台任务使用 WorkManager 恢复执行。
4. 先做有限重试与失败条目重试；暂不做跨项目并发、全局翻译记忆自动合并、多轮 agent 调度和复杂术语自动生成。
5. 译文先保存到 TYN 项目工程；导出仍由项目卡片的导出操作选择格式与位置。

这些属于架构建议，不修改 `SPEC.md` 的当前行为定义。功能实现后再把验收行为同步到 `SPEC.md`、`ARCHITECTURE.md` 和持久化数据清单。
